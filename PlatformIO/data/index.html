Sensors

Each sensor plugs into a JST PA-3 socket: pin 1 = switched 5 V, pin 2 = signal (0-6.3 V), pin 3 = ground. The value is what goes out on CAN and what can2gauge shows as ADC 1-8. Set each one up on the Sensors tab.

Display options

Tick a sensor to show it as a dial gauge instead of a number (remembered in this browser). The two boxes are the dial's minimum and maximum, saved on the adc2can and sent to can2gauge with the rest of the sensor's settings, so a gauge page showing this sensor uses the same range. Blank = Auto, worked out from the sensor's scaling.

Every sensor's value (as sent on CAN), the valid / rail-fault flags and the battery voltage, at the chosen rate, in the board's own 12 MB log memory - kept through power cuts and web UI updates. "Automatically at power-up" starts a new log every time the car is switched on (no clock on the board: those logs are timed from power-up).

Logs

CSV opens in Excel / LibreOffice / any plotting tool: one row per record, time in seconds (and the date and time when the log was started from this page), one column per sensor in its units, then the battery and the flag bits. Raw is the log as stored on the board (.a2c).

Trends - last 10 minutes

One-second averages, kept on the board, so the last 10 minutes are here as soon as you open this tab - whether or not a log is recording. Amber lines are the sensor's low / high warning. Hover or touch a graph to read a value.

Sensor channels

Linear: value = scale × volts + offset (pick a preset for common senders). Table: up to 8 volts:value points, straight lines between them. NTC: a thermistor to its own 5 V rail through the board's pull-up R_PUn (fit 2.2k for a Bosch NTC); beta model, the 21k input divider is allowed for. Ratiometric: the reading is scaled to a 5.000 V supply using that sensor's measured rail. Leave it off for sensors with their own supply (a wideband controller output, an EGT amplifier). The name (14 characters) and unit go to can2gauge as the gauge label. Changes save as you make them and go out on CAN straight away.

Rail protection

Each sensor's 5 V comes through its own TPS4H160A switch (about 0.5 A limit). A short or overload raises its fault flag, or pulls the rail below the "rail low" level; after the hold time it counts as a fault. Back-feed: 12 V pushed onto a sensor's 5 V pin lifts the whole sensor bus, so every rail switches off. They come back once the bus is normal again, and never sooner than the retry time after it started.

Power

Below "no 12 V" the board is on USB power alone: the sensor supply is off, so rail faults are not raised. Battery low / high go out in the CAN status frame.

CAN bus

Frames use 29-bit ids, base + board × 16 + 0..13, so they cannot collide with any 11-bit VAG / OBD frame on a shared bus. can2gauge's ADC tab must have the same base id (default 0AD2C000); board 2 shows there as sensors 9-16. A new speed applies at once.

Values are float32 big-endian in engineering units (NaN when a sensor is not valid). The status frame carries the valid / rail / fault / out-of-range masks, the flags, the sensor bus and the battery. Names, units and every channel setting are shared on the bus, so a can2gauge shows - and can edit - exactly what is set here (ids +12 / +13 come from the gauge).

WiFi

A new name or password applies when you leave the field: the access point restarts, so rejoin it under the new name. Joining your home / garage WiFi (for updates from GitHub) is on the OTA tab.

Wireless to can2gauge (ESP-NOW)

Sends exactly what goes out on CAN (values, names, units, settings) as a WiFi broadcast as well, so a can2gauge with just power - no CAN wire - shows these sensors. No pairing. One-way: changing this board's settings from a gauge still needs CAN. The gauge must be on the same WiFi channel (both start on channel 1); joining a home network on either side can move it.
Sends every frame received from the car's CAN to can2gauge gauges over WiFi, so a gauge with power only - no CAN wire - reads the car as if it were wired: its CAN profile, the CAN monitor, DBC and user signals. A busy 500 kbit/s bus is around 2000 frames a second; if frames are lost, cap each ID's rate. It rides on the WiFi broadcast to gauges, so that has to be on too.
